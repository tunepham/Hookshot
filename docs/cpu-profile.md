# Where the CPU goes: a profile of Hookshot

This page explains how a frame of the game spends CPU time on a PC: which threads run, what each part of the code does, what it costs, what limits the frame rate, and which work could be removed or done more cheaply. The measured part is generated by `scripts/cpu_report.py` from sampled runs, so it can be redone for any build without editing this page by hand (see *Regenerating it* below). It holds no game files and nothing made from them: all of the game's own code is one row, *lifted game code*, with no function, address or subsystem of the game named.

Each scene below is generated by `scripts/cpu_report.py` (see *Regenerating it*); nothing between its markers is edited by hand.

### At a glance

- **Speed:** 51.2 fps and 73.7 ms of CPU a frame (3.73 cores), median of 5 runs without the sampler; 8 frames over 100 ms in all of them.
- **Where the CPU goes:** game 167.7 %, render 70.3 %, os 62.1 %, runtime 7.7 %, system 1.9 % of a core; the largest parts: game/lifted 167.7 %, os/sync 23.9 %, render/memory-and-mirrors 21.0 %, render/replay-and-submit 19.6 %, render/draw-translation 15.1 %.
- **sead::MainThread:** running 25.8 % of the time; it waits most in `nn::os::WaitLightEvent from lifted game code` (33.7 %) and `hos_cv_sleep from lifted game code` (19.2 %).
- **Presentation_Thread:** running 63.1 % of the time; it waits most in `nn::os::ReceiveLightMessageQueue from lifted game code` (32.6 %) and `nvnQueueSubmitCommands from lifted game code` (2.4 %).
- **Largest estimated savings:** The 20 us spin before an event or queue wait sleeps (0.75 to 1.19 ms a frame); The scan for written pages at every submission (0.59 to 0.88 ms a frame); Every mutex lock and unlock through the host's object table (0.41 to 0.83 ms a frame).
- **On the serial threads** (the main and Presentation threads, where a saving is most likely to shorten the frame): The scan for written pages at every submission (5.9 % of a core there); Each recorded command buffer copied when its recording ends (1.3 % of a core there); The submitting thread moved onto the reserved core and back for every replay (1.7 % of a core there).

### What limits the frame

Three things can set the frame time: the GPU, when its time a frame is close to the frame time; one of the two serial threads below, when it is on the CPU nearly all the time; or the chain of waits between threads. #### The frame's two serial threads: running, and what they wait in

The game's main thread (`sead::MainThread`) builds each frame's commands; the game's `Presentation_Thread` submits them, and with the default `RX_VK_ASYNC=0` the renderer replays each submission on Vulkan on that same thread. When neither is saturated, the frame is paced by what each waits for: the other thread, the game's job workers (when the main thread waits for their jobs, their work is on the frame's path too), or the GPU and the display.

| thread | running | waits in (top 6, % of the thread's samples) |
|---|---|---|
| sead::MainThread | 25.8 % | `nn::os::WaitLightEvent from lifted game code` 33.7 %; `hos_cv_sleep from lifted game code` 19.2 %; `nvnWindowAcquireTexture from lifted game code` 12.5 %; `nvnQueueSubmitCommands from lifted game code` 4.7 %; `nn::os::SleepThread from lifted game code` 2.9 %; `lifted game code` 0.5 % |
| Presentation_Thread | 63.1 % | `nn::os::ReceiveLightMessageQueue from lifted game code` 32.6 %; `nvnQueueSubmitCommands from lifted game code` 2.4 %; `nvnQueuePresentTexture from lifted game code` 1.5 %; `nn::os::SleepThread from lifted game code` 0.2 %; `nvnQueueSubmitCommands` 0.1 %; `nn::os::LockMutex from lifted game code` 0.0 % |

**Reading:** the GPU takes 9.1 of the 20.0 ms a frame and neither serial thread is saturated (the busiest thread overall: `Presentation_Thread`, 63.1 %), so the frame is most likely paced by the chain of hand-offs between threads; `sead::MainThread` runs 25.8 % of the time and waits most in `nn::os::WaitLightEvent from lifted game code` (33.7 %); `Presentation_Thread` runs 63.1 % of the time and waits most in `nn::os::ReceiveLightMessageQueue from lifted game code` (32.6 %). So the frame's path runs through the serial threads' own work and the work they wait for; a saving there can raise the frame rate, while a saving elsewhere frees CPU. Sampling shows where the threads wait, not which awaited job finishes last in each frame, so it cannot say which saving raises the frame rate most; a per-frame trace of the job system would settle that.

### What limits the frame

Three things can set the frame time: the GPU, when its time a frame is close to the frame time; one of the two serial threads below, when it is on the CPU nearly all the time; or the chain of waits between threads. #### The frame's two serial threads: running, and what they wait in

The game's main thread (`sead::MainThread`) builds each frame's commands; the game's `Presentation_Thread` submits them, and with the default `RX_VK_ASYNC=0` the renderer replays each submission on Vulkan on that same thread. When neither is saturated, the frame is paced by what each waits for: the other thread, the game's job workers (when the main thread waits for their jobs, their work is on the frame's path too), or the GPU and the display.

| thread | running | waits in (top 6, % of the thread's samples) |
|---|---|---|
| sead::MainThread | 30.4 % | `nn::os::WaitLightEvent from lifted game code` 37.5 %; `nvnWindowAcquireTexture from lifted game code` 16.3 %; `hos_cv_sleep from lifted game code` 6.0 %; `nn::os::SleepThread from lifted game code` 4.4 %; `nvnQueueSubmitCommands from lifted game code` 2.3 %; `nvnCommandBufferAddControlMemory from lifted game code` 0.8 % |
| Presentation_Thread | 49.7 % | `nn::os::ReceiveLightMessageQueue from lifted game code` 46.8 %; `nvnQueuePresentTexture from lifted game code` 1.6 %; `nvnQueueSubmitCommands from lifted game code` 1.4 %; `nn::os::SleepThread from lifted game code` 0.2 %; `nn::os::UnlockMutex from lifted game code` 0.0 %; `std::thread::join` 0.0 % |

**Reading:** the GPU takes 4.8 of the 13.9 ms a frame and neither serial thread is saturated (the busiest thread overall: `Presentation_Thread`, 49.7 %), so the frame is most likely paced by the chain of hand-offs between threads; `sead::MainThread` runs 30.4 % of the time and waits most in `nn::os::WaitLightEvent from lifted game code` (37.5 %); `Presentation_Thread` runs 49.7 % of the time and waits most in `nn::os::ReceiveLightMessageQueue from lifted game code` (46.8 %). So the frame's path runs through the serial threads' own work and the work they wait for; a saving there can raise the frame rate, while a saving elsewhere frees CPU. Sampling shows where the threads wait, not which awaited job finishes last in each frame, so it cannot say which saving raises the frame rate most; a per-frame trace of the job system would settle that.

## How the numbers are made

- **The standard test.** Hyrule Field from a save, the camera turning at full speed (the right stick held fully right from the moment the area has loaded), so new scenery streams in every frame. It's the heaviest steady CPU case found so far.
  - The frame rate is unlocked (`HOS_FPS_MAX=240`), so the PC sets the pace, not the 60 fps cap.
  - The game clock is checked with `HOS_FPS_LOG=1`. A valid run reads 1.000 ± 0.01; a game running fast or slow would otherwise look like a frame-rate change.
  - The window is 2560x720 (32:9). The measured window is 20 s from the moment the area has loaded, with warm caches.
- **Two kinds of runs.**
  - *Unsampled* runs give each scene's fps, CPU ms a frame (the process's CPU time ÷ frames) and frame times. That is the *Measured without the sampler* table.
  - *Sampled* runs (`HOS_SAMPLE_ALL`) give the shares. Every 2 ms they record the call stack of each game and renderer thread. Sampling costs some frame rate, so the frame time in *What limits the frame* is that of the sampled runs and is longer than the headline's.
- **Occupancy, not CPU milliseconds.** A sample counts as on the CPU when its innermost frame is not a waiting system call. That includes a thread that is ready but preempted, and leaves out time in the kernel. The *Runs* table compares the sampled total with the measured process CPU.
- **Units.**
  - **% of a core:** 100% is one CPU core busy for the whole measured time.
  - **ms a frame:** a share converted with that run's own frame rate (share × 10 / fps), then the median of the runs. Totals are added up within each run before the median is taken, so a total can differ from the sum of the medians below it.
- **Three views of the same samples.**
  - **Owner:** the work is charged to the first of Hookshot's own functions above it, so a Windows sleep under the host's `WaitLightEvent` counts as the host's synchronization.
  - **Self:** the work is charged to the function the CPU was executing.
  - **Inclusive:** every sample with the function anywhere in its stack.
- **The window right after a load still streams.** The game decompresses newly loaded scenery on its loading threads during the first seconds of every scene. That work is in the numbers, beside the frame's path.
- **Instrumentation.** The bench writes a line per present to a file (`HOS_PRESENT_TRACE`), on the Presentation Thread. Its file writes show as system time under the host's present call. This is a bench cost, not shipped behaviour.
- **Names.** Thread names are the ones Hookshot's log prints for every run (`hookshot_log.txt` holds no game data). The game's own functions are not listed one by one: all lifted code is one row, and a wait the game asked for is named by the Hookshot entry it called (`nn::os::WaitLightEvent from lifted game code`). A description is of Hookshot's own code, the driver or the system, and a description with a measurement in it is cut to its behaviour: every number on this page comes from the capture.

## The categories

| category | what it is |
|---|---|
| **game** | The game's own code, translated from the Switch's ARM code to C ahead of time (`code_*.o`): one category, `game/lifted`, and one row in the function tables. |
| **runtime** | What translated code needs to run on a PC: finding the target of indirect calls, the floating-point helpers that give exact ARM results, atomics and the write marks the renderer reads, and the polls that let threads give up their core. These are counted here even when they're compiled into the game code's own objects. |
| **os** | Hookshot's own implementation of the Switch's operating system (`host/`). It covers locks, events and waits; threads and the virtual cores that keep the game's six-core assumptions true; sleeps; memory; the NVN graphics calls' bridge to the renderer; audio, input, files, video decoding. |
| **render** | The Vulkan renderer (`gpu/vk/`). It replays the game's NVN graphics commands: capture of the game memory a frame reads, translation of draws and their descriptors, textures, shaders and pipelines, submission and presentation, upscaling and frame generation, the menu. |
| **driver** | The GPU driver's own CPU work, called by the renderer. |
| **system** | Windows itself, running on the CPU: waking threads, the work around sleeping and locking, reading the clock, the heap. Time a thread spends blocked in Windows is not here; it is in *Blocked*. |
| **crt** | `memcpy` and similar runtime functions; in the owner view they count to the code that called them. |
| **external** | Other modules loaded into the process (overlays, graphics runtimes) that no rule names; in the owner view they count to the code of ours that called them. |
| **tooling** | Profilers and diagnostics; near zero unless switched on. |
| **unclassified** | Code of Hookshot's own that no rule covers yet. A new upstream file shows up here first (see below). |

## Regenerating it

1. **Build** the game from the commit to profile. Keep the linker maps (`hookshot.map`, `hookshot_vk.map`) of that exact build; the map's timestamp matches the binary's.
2. **Capture each scene**, one game at a time, with these switches beside the scene's own:
   `HOS_FPS_MAX=240 HOS_FPS_LOG=1 HOS_WINDOW_SIZE=2560x720 HOS_ASPECT=3.5556 HOS_PRESENT_TRACE=<run>/presents.csv`
   - **Unsampled runs:** at least three; this is the *Measured without the sampler* table.
   - **Sampled runs:** at least three, with `HOS_PROFILE=5 HOS_SAMPLE_ALL=<run>/all.txt`. The sampler records while the file `<run>/all.txt.go` exists, so create it at the start of the measured window and delete it at the end.
   - **One run for call counts** (optional) with `HOS_HLE_STATS=1`. The HLE call counters are not in `main` yet: the counts on this page come from a build of the same commit with a local diagnostic that counts each HLE entry and logs `hle:` summaries every 5 s. Without such a build leave `--calls` out; the function tables then have no calls column, and `--calls` on a run with no `hle:` lines is refused rather than ignored.
3. **What a run folder must hold:**

   | file | contents |
   |---|---|
   | `all.txt` | the sampler's lines, `<ms> <thread>\|<frame>;<frame>;...`, innermost frame first, each `module+offset` |
   | `presents.csv` | the present trace: `frame,return_ns,interval_ns` |
   | `load.json` | the measured window: `window_present_s` (start and end, seconds from the first present on the same clock as `presents.csv`) and `window_cores` (the process's CPU over the window ÷ its length) |
   | `game.log` | the run's `hookshot_log.txt`: the version line, the GPU line, `vi: game clock` lines, the renderer's per-frame lines and, for call counts, the `hle:` summaries |
   | `process.json` | optional: the run's switches (`env`), for the switches line |
   | `hookshot_options.ini` | optional: a copy of the game folder's options file as it was for the run, for the Insert-menu line; without it, say what the runs used with `--menu` |

4. **Generate each scene's section in place:**

   ```sh
   python -I scripts/cpu_report.py <sampled run>... --measured <unsampled run>... --calls <counter run> \
       --maps <maps folder> --readobj <llvm-readobj> --hashes <sha256 list of the binaries> \
       --machine "<CPU, RAM, OS, driver version>" [--menu "<Insert-menu options the runs used>"] --title "<scene>" \
       --into docs/cpu-profile.md --section <scene key>
   ```

   `--readobj` names Windows' system DLL exports. The script reads Windows captures with lld-link maps only; a Linux capture (`hookshot`, `hookshot_vk.so`) is refused with a message, not mislabelled.
5. **Maintain the data files:**
   - When the report lists **unclassified** code, add a rule to `scripts/cpu_categories.py`.
   - When it lists functions **not yet described**, add a line to `scripts/cpu_functions.json`.
   - When a fix lands, update its row in `scripts/cpu_candidates.json`.

Rules are keyed on module, object file and function names, never on addresses of Hookshot's binaries, so they survive rebuilds.

A developer can split lifted code further on their own PC: `--guest-map` (a map of the game's functions and subsystems), `--functions` (more descriptions) and `--candidates` (more candidates) take local files. Those are made from the game binary, so they and anything generated with them stay on that PC; the published page is always made without them, from the repository alone.
